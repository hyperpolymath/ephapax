= ephapax coprocessor boundary
:toc: macro

toc::[]

== What this is

ephapax's **own** *thin typed dispatch boundary* for coprocessors — ten
capability classes (Audio/Crypto/Maths/Physics/GPU/Vector/Tensor/Quantum/
IO/FPGA) reached over a single C-ABI seam, with the language's linear types
guarding the device-buffer lifecycle.

The DESIGN follows the pattern Axiom.jl demonstrated (capability classes +
linear buffers + a thin FFI seam, covering the full range of coprocessor
types). ephapax *models* that pattern — it does **not** import, depend on,
co-own, or forward to Axiom. The seam is ephapax's own, and the boundary is
deliberately clean (no framework internals cross into the language):

[cols="1,3"]
|===
| `stdlib/Coproc.eph` | The typed ephapax surface: a `Capability` sum type (the ten classes), a `cap_tag` wire-tag map, and a LINEAR `CoprocBuf` device-buffer handle with an `upload → dispatch* → (download \| release)` lifecycle. Type-checks under `ephapax check`.
| `tools/coproc/ephapax_coproc.zig` | The single C-ABI seam: a Zig shared library exporting flat `eph_coproc_*` symbols (`i64 (...) -> i64`) that dispatch to whatever native coprocessor backend is linked behind them. The in-tree build is a STUB (reports unavailable, with one loopback for the seam test). No external framework, no Julia, no Axiom runtime.
| typed `extern` block | `Coproc.eph` declares the five `eph_coproc_*` symbols in an `extern "ephapax_coproc" { ... }` block. Raw variadic `__ffi` is rejected since v2 plan rung E1, so this is the only FFI path. The full port (wire types, a host binding for the `ephapax_coproc` import module, the `CoprocBuf` linearity annotation) is rung E10.
|===

== The safety story (why a language, not a library, owns this)

A `CoprocBuf` is a *linear resource*. Consumers bind it with `let!`, so the
linear checker guarantees a device buffer is consumed **exactly once** —
no use-after-download, no double device-free, no silently-leaked buffer
(a dropped handle is a type error). `dispatch` consumes a buffer and
returns a fresh one (consume-and-reborrow); `download` and `release` are
the two terminal consumers. This is the same discipline `Region!` and the
streaming `MessageHandle` use.

NOTE: In the current v2 grammar, linearity is expressed at `let!` *binding
sites*, not via `T!` *type annotations* (see
`docs/v2-grammar-and-codegen-gaps-2026-06-16.adoc`). `Coproc.eph` therefore
declares plain `CoprocBuf` and relies on consumer `let!` bindings for the
linear guarantee.

== Build & use

NOTE: Since v2 plan rung E1 (2026-11-09) the type checker rejects raw
`__ffi`, so `ephapax run --interp ... -L libephapax_coproc.so` no longer reaches the
shim: the interpreter's `-L` loader serves only raw `__ffi` calls and does
not yet bind `extern` declarations. Since rung E4 `ephapax run` executes the
compiled wasm, and `-L` is accepted only with `--interp` (the legacy
interpreter). The 42-vs-0 proof below is historical.
Re-wiring the seam through `extern` is rung E10.

[source,sh]
----
# Build the (stub) seam:
zig build-lib -dynamic -O ReleaseSafe \
    tools/coproc/ephapax_coproc.zig -femit-bin=libephapax_coproc.so

# HISTORICAL (pre-E1, raw `__ffi` only). This no longer reaches the shim;
# do not use it to test typed Coproc dispatch until rung E10:
ephapax run --interp myprog.eph -L libephapax_coproc.so
----

Verified end-to-end: a program calling `eph_coproc_dispatch(_, _, 20, 22)`
returns `42` with the shim linked, and falls through to ephapax's built-in
`[ffi:stub] -> 0` when it is not — proving the `__ffi` path reaches this
shim.

== Wiring status (honest)

*WIRED:* the seam build target (`just build-coproc` / `just test-coproc`).
The raw `__ffi` path that reached it (the 42-vs-0 proof above) was retired
by rung E1; `Coproc.eph` now declares the symbols in a typed `extern`
block, which type-checks and compiles to wasm imports from the
`ephapax_coproc` module, but no host binds that module yet (rung E10).

*NOT YET WIRED:* no `.eph` program can use the *typed* `Coproc` API. The v2
toolchain has no working module-import + qualified-member access, so
`import Coproc; Coproc.upload(…)` neither parses (`Coproc.Tensor` →
"construct_expr") nor resolves (`import` does not bring members into scope →
"unknown constructor"). This is the **same keystone gap that strands the
whole stdlib** (Region/Stream/… are equally un-consumable) — see
`docs/v2-grammar-and-codegen-gaps-2026-06-16.adoc`. The typed
surface is a *foundation*, not yet a consumable feature.

== Wiring a real backend

The `// TODO(backend)` markers in `ephapax_coproc.zig` are the exact
extension points. Each `eph_coproc_*` symbol selects a coprocessor unit from
its capability tag and dispatches to the native backend's kernel for that
op. ephapax keeps the typed surface + the linear gate; the backend behind
the seam owns routing, fallback, and kernels. The backend is ephapax's to
choose (native, vendor SDK, or a separate process) — it is **not** part of,
nor coupled to, any external framework.

An optional `CoprocResult` round-trip proof for the status contract can be
added to `src/abi/Ephapax/ABI/Foreign.idr` (mirroring `CompileResult`),
checked by `abi-verify.yml`.
